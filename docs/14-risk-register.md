# 14 — Risk Register

Likelihood/impact are qualitative (Low/Med/High), reassessed at each roadmap phase gate rather than treated as fixed at Phase 1.

| # | Risk | Likelihood | Impact | Mitigation | Owner phase |
|---|---|---|---|---|---|
| 1 | Chosen crypto library (vodozemac) integration friction in-browser (WASM size/perf, API ergonomics for our envelope format) forces a late switch to the hand-rolled X3DH/Double-Ratchet fallback | Med | High (delays Phase 3, increases review burden) | Decision-gate spike explicitly scheduled *before* Phase 3 commits, not discovered mid-implementation — see [05-crypto-architecture](05-crypto-architecture.md) | Phase 2→3 |
| 2 | No-Docker deployment means environment drift between developer machines and production (different OS package versions of Node/Postgres client libs etc.) | Med | Med | Pin exact versions via `engines` field + a documented target OS/Node version for production; managed Postgres/Redis removes the two riskiest version-drift surfaces | Phase 12 |
| 3 | Self-hosted coturn becomes a single point of failure / scaling bottleneck for calls as usage grows | Med | Med | Documented as self-hosted by explicit choice (privacy tradeoff accepted); revisit with a second coturn instance + DNS-based failover if call volume grows, not a Phase 1 blocker | Phase 6+ |
| 4 | Admin-provisioned-only registration becomes an onboarding bottleneck if the platform needs to grow beyond a small, admin-known user base | Low (matches current stated intent) | Med if intent changes later | Explicitly flagged as a future redesign point in [13-roadmap](13-roadmap.md), not treated as permanent | Future |
| 5 | Password-only baseline auth (no forced MFA) is weaker than passkey-first against credential stuffing/phishing | Med | Med | Rate limiting + lockout now; optional WebAuthn/TOTP step-up shipped in Phase 9, not indefinitely deferred | Phase 9 |
| 6 | Browser-based key storage cannot fully protect against a compromised browser/extension (inherent web-platform limitation) | Med | High if it occurs | Non-extractable keys + in-memory-only KEK reduce blast radius; disclosed honestly rather than papered over — see [08-threat-model](08-threat-model.md#compromised-browser) | Ongoing |
| 7 | Megolm group-session rotation-on-removal has a brief window between removal and full member re-keying where implementation bugs could leak a message to a just-removed member | Low if implemented per spec | High if it occurs | Dedicated crypto test coverage for exactly this scenario ([12-testing-strategy](12-testing-strategy.md)); code isolated to `packages/crypto/src/group` for focused review | Phase 5 |
| 8 | Solo/small-team operational load (no Docker, self-hosted coturn, managed-but-still-operated Postgres/Redis) increases the chance of a missed patch/misconfiguration versus a fully managed stack | Med | Med | Dependency/secret scanning in CI, documented runbooks in `infrastructure/`, backup-restore testing on a schedule ([11-deployment-architecture](11-deployment-architecture.md)) | Ongoing |
| 9 | Contact-discovery mechanism (deferred) gets implemented later under time pressure without the privacy-preserving design spike it needs | Low (explicitly gated in the roadmap) | High if skipped | Roadmap explicitly requires its own design review before implementation, not bundled into a generic "contacts" ticket | Future |
| 10 | Push provider (Web Push service, later FCM) outage or API change silently breaks notification delivery without affecting in-app messaging (which still works over WS) | Med | Low | Notification delivery failure is independent of message delivery by design (push is a convenience trigger, not the transport) — monitored but not a data-loss risk | Phase 7+ |
| 11 | Object storage bucket misconfiguration (accidentally made public) exposes ciphertext blobs | Low | Low (content is still encrypted) / Med (confirms conversation activity patterns via object timing/size) | Bucket-policy check in deployment runbook + periodic automated check that the bucket rejects unauthenticated `GET`/`LIST` | Phase 4, Phase 12 |
| 12 | Argon2id parameters chosen in Phase 2 turn out too light (or too heavy for login latency) once real production hardware is known | Med | Med | Parameters are versioned in the hash string itself, allowing a rolling upgrade on next login without forcing a mass password reset | Phase 2, revisited Phase 12 |

## Review cadence

This register is revisited at the end of every roadmap phase (not just once) — a phase isn't considered closed if it introduced a new risk that wasn't logged here.
