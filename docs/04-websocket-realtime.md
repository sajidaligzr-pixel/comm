# 04 — WebSocket / Realtime Architecture

**Revision note**: implemented via `apps/web/server.ts`, a custom Next.js server — a plain Node `http.Server` that hands normal HTTP requests to Next's request handler and, on the server's `upgrade` event for the `/realtime` path, hands the connection to a `ws.Server` instead (no separate NestJS WebSocket gateway/Fastify process). See [00-overview](00-overview.md) and [01-folder-structure](01-folder-structure.md).

## Transport & auth

Single authenticated WebSocket connection per device (`wss://.../realtime`), upgraded only after the access token is validated during the HTTP upgrade handshake (short-lived token, same one used for REST — no separate weaker WS auth path; the same `requireAuth()` helper the Route Handlers use is called here against the upgrade request's cookies before `ws.Server` completes the handshake). The socket is bound to `(userId, deviceId, sessionId)` server-side at connect time; every inbound event is authorized against that binding, never against a client-claimed field in the message body. A revoked session/device is force-disconnected immediately (the revoke handler publishes to Redis, every `apps/web` process holding that socket closes it — see [06-device-architecture](06-device-architecture.md)).

Multiple tabs/processes: each browser tab opens its own socket (its own `deviceId`-scoped identity isn't shared — see multi-device model in [06](06-device-architecture.md)); fan-out to "all of a user's devices" is done server-side via a Redis-backed registry of `userId → [socketId...]` per process, not by the client.

## Scaling across processes

Redis pub/sub is the cross-instance bus: when one `apps/web` process needs to deliver an event to a device connected to a different process (multiple PM2/systemd instances behind the reverse proxy, see [11-deployment-architecture](11-deployment-architecture.md)), it publishes to a per-device Redis channel; the owning process (subscribed) forwards to its local socket. Presence and typing state live in Redis with short TTLs (ephemeral by design — see [10-privacy-data-retention](10-privacy-data-retention.md)), not in Postgres.

`apps/worker` also subscribes to `MESSAGE_EVENTS_CHANNEL` (not just `apps/web`) — its push-notification dispatch (docs/13-roadmap.md's push notification pass, `apps/worker/src/realtime/push-dispatch.ts`) reacts to the same `new` events a connected device's socket would, deciding whether to send a Web Push for devices that either aren't currently connected or just haven't opened the relevant tab. This is why `MESSAGE_EVENTS_CHANNEL`'s channel name and `MessageEvent` union live in `@comm/types` rather than `apps/web` — a second, independent app subscribing to the exact same channel is the whole reason that boundary exists (see the `deleted` event row below for the first case this pattern was built for).

## Event catalog

**Shipped (Phase 3)** — inbound events are validated Zod envelopes (`apps/web/server/realtime/message-handlers.ts`); outbound events are the `MessageEvent` union published over Redis (`apps/web/server/realtime/bus.ts`) and forwarded verbatim to the target device's socket(s):

| C→S | `message.read` | `{ type, conversationId, upToMessageId }` | Advances `conversation_members.last_read_message_id`; server checks the reader's `read_receipts` privacy setting before fanning out (not the sender's) |

## Reconnection & delivery guarantees

- **At-least-once, idempotent.** Every message carries a client-generated UUIDv7 id; the server's insert is `ON CONFLICT (id) DO NOTHING`, so a client that retries a send after a dropped ack never creates a duplicate. Clients dedupe incoming `new` events by id for the same reason (a redelivery after reconnect is a no-op, not a duplicate bubble).
- **Reconnect backoff**: exponential with jitter, capped 1s → 30s (`apps/web/lib/realtime-client.ts`), resets to the fast end on a successful connect. Respects close code `4001` (device revoked) by not reconnecting at all.
- **Missed-event catch-up — shipped, simpler than originally designed.** There is no `sync.required` server push and no cursor negotiated over the socket. Instead, the open conversation thread simply re-fetches via `GET /conversations/:id/messages` whenever the connection (re)opens, which is sufficient at Phase 3's scale (a page/tab with one open conversation) but not yet a general per-conversation-list catch-up — that's a real gap to close before Phase 3's guarantees extend to "every conversation in the sidebar," not a documentation lag.
- **Multiple tabs**: each tab is its own device identity, so "duplicate delivery across tabs" isn't a special case — it's just two devices receiving the same message, each with its own delivery/read tracking. Read state at the *conversation* level (for unread-count purposes) is reconciled via `conversation_members.last_read_message_id`, which any of the user's devices can advance.
- **Server restart**: sockets drop, clients reconnect via the backoff above and catch up via the refetch-on-reconnect behavior above — no in-memory state the server holds is authoritative (Postgres and Redis are), so a restart never loses data, only causes a brief reconnect.

## Call signaling — shipped (1:1 audio, ahead of the rest of Phase 6)
<a id="call-signaling"></a>
Call setup/teardown and SDP/ICE exchange ride the same authenticated socket under a `call.*` namespace, per the event catalog above — one authenticated channel to secure and monitor, not two (`server/realtime/message-handlers.ts`). The server relays signaling blindly between the two conversation members (authorized by re-deriving membership on every event, the same pattern as `message.send`/`typing.*`, not a separate `call_participants` table — see docs/02-database-schema.md's note on why call *history* persistence is still a real gap); it does not, and structurally cannot, inspect SDP contents to affect the call. Media itself never touches this channel or the API server — see [11-deployment-architecture](11-deployment-architecture.md) for the TURN path, and [08-threat-model](08-threat-model.md#call-security) for the full security reasoning. Shipped as **audio-only, direct conversations only, no group calls, no minimize-to-bubble** — a deliberately narrow slice, with video/group/call-history explicitly still open (docs/13-roadmap.md).

## What the server does *not* do here

It doesn't decrypt `ciphertext` to decide anything (routing is by `conversationId`/membership, not content). It doesn't infer `content_type_hint` from the payload — the sender asserts it, and a lying client can only misrender its own message for others (a client-side annoyance, not a security boundary). It doesn't hold typing/presence state longer than a short TTL — see [10-privacy-data-retention](10-privacy-data-retention.md).
