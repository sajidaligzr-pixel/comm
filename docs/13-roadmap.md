# 13 — Development Roadmap

Incremental, per master-prompt §99/§104: each phase ships working, tested functionality before the next starts; no attempt to build the entire system in one pass.

## Phase 3 — One-to-one encrypted messaging ✅
**Shipped.** `packages/crypto` built from scratch on `@noble/curves`/`@noble/hashes`/`@noble/ciphers`, implementing X3DH ([signal.org spec](https://signal.org/docs/specifications/x3dh/)) and the Double Ratchet ([signal.org spec](https://signal.org/docs/specifications/doubleratchet/)) directly against Signal's published pseudocode — a reversal of Phase 1's vodozemac-primary recommendation, made after finding no well-maintained thin vodozemac WASM binding in the npm ecosystem (only the heavy official `@matrix-org/matrix-sdk-crypto-wasm` and unmaintained community bindings); see [05-crypto-architecture](05-crypto-architecture.md#library-decision) for the full comparison. 30 crypto unit tests covering forward secrecy, post-compromise recovery, out-of-order/skipped-message-key handling, and tamper detection.

Shipped end-to-end: per-device identity/signed-prekey/one-time-prekey generation and upload, key-bundle publish/claim API ([03-api-design](03-api-design.md)), direct-conversation creation, X3DH session establishment on first message, Double-Ratchet-encrypted send/receive over both WebSocket (primary) and REST (offline-queue fallback), delivery + read receipts, typing indicators, and a local IndexedDB store — keys, ratchet sessions, and a decrypted-plaintext message cache, all wrapped under an Argon2id-derived KEK from the user's login password — that is the actual source of chat history on reload, since Double Ratchet message keys are single-use and ciphertext is not re-decryptable after first use (see [05-crypto-architecture](05-crypto-architecture.md#local-key-storage)). Verified: a server-side integration test decrypts nothing and asserts the stored row is opaque ciphertext + envelope header; `tsc`, `eslint`, and `next build` all clean; 88 tests passing across the monorepo.

**Explicitly not in scope for Phase 3, tracked rather than glossed over:**
- **Single recipient device only.** `sendMessage` addresses exactly one recipient device per conversation (see `getPrimaryRecipientDevice`'s docstring) — real multi-device fan-out (a sender's own other devices, a recipient with more than one active device) is deferred. The schema (`message_recipients`) is already shaped for it.
- No `sync.required`/cursor-based reconnect catch-up across the whole conversation list yet — the open thread refetches via REST on reconnect, which covers Phase 3's single-open-conversation scale but not a full sidebar catch-up ([04-websocket-realtime](04-websocket-realtime.md)'s Reconnection section).
- No message reactions API/UI (table exists, unused), no message editing UI (schema supports `edited_at`), no `blocked_users` enforcement on `/conversations/direct` (table doesn't exist yet — Phase 9).
- No presence (`online`/`last seen`) or `key.changed` (identity-key-rotation notice) events.

### Post-Phase-3 UI/polish pass ✅
**Shipped**, as a dedicated redesign pass rather than piecemeal: a WhatsApp-style responsive chat UI (`app/(app)/chats/layout.tsx` + `components/chat/chats-shell.tsx` — persistent sidebar + pane on desktop, single-pane with a back arrow on mobile), delivered/read tick icons (seeded from the initial fetch, not just live WS events — a real bug in the original Phase 3 UI, fixed here), date separators, message grouping, an emoji picker, live sidebar previews/unread badges (sourced only from the local decrypted cache — see `chats-shell.tsx`'s decryption-safety note on why it never decrypts a message the open thread is also decrypting), reply-to (send + quoted-preview rendering), and message deletion with **live cross-device propagation** (a `deleted` WS/Redis event, not just a server-side tombstone — see [04-websocket-realtime](04-websocket-realtime.md)).

**Disappearing messages ✅ — shipped**, closing the Phase 3 gap noted above: `PATCH /api/conversations/:id` sets the timer (either member may change it), `apps/worker`'s hourly sweep (`jobs/cleanup.ts`) is what actually enforces it (tombstones expired messages the same way a manual delete does, and publishes the same live `deleted` event), and the open thread additionally prunes locally on a 30s client-side timer for a more immediate feel than waiting for the hourly sweep. `MESSAGE_EVENTS_CHANNEL` and the `MessageEvent` union moved to `@comm/types` specifically so `apps/worker` — a background job, not a request handler — can publish the identical wire shape without importing from `apps/web`.

**A slice of Phase 4 shipped early: real voice messages.** Recorded client-side (`MediaRecorder`, capped at 2 minutes, 32kbps opus), encrypted through the *exact same* X3DH/Double-Ratchet envelope as text (`contentTypeHint: 'voice'` — the "plaintext" is just raw audio bytes; no new crypto, no new wire path), sent over the same REST endpoint. This is **not** the general media/attachment pipeline below (no object storage, no arbitrary file types, no thumbnailing) — it works because a compressed voice note is small enough to fit through the same inline-ciphertext path text already uses. Images followed the same pattern shortly after (below); video still needs the real signed-upload design.

**A slice of Phase 8 shipped early: PWA installability**, not full offline support. `app/manifest.ts` (Next's manifest route convention), generated PNG icons (192/512/maskable — rasterized from the existing `app/icon.svg` mark), a deliberately minimal `public/sw.js` (pass-through fetch handler — exists only to satisfy the browser's installability check, explicitly not an offline cache), and `components/install-prompt.tsx` (custom "Install Comm" banner on `beforeinstallprompt`, an instructional variant for iOS Safari where that event doesn't exist). The real offline app-shell/Workbox caching strategy is still Phase 8, not attempted here.

**One thing considered and explicitly deferred, not silently skipped, during this pass:**
- **Biometric/PIN unlock.** Asked for directly, including a suggestion to replace the account password with a 6-digit numeric PIN. Refused in that form: the login password is also what derives the local KEK protecting every local key/message ([05-crypto-architecture](05-crypto-architecture.md#local-key-storage)), so lowering it to ~10⁶ possibilities would make both the account *and* the offline-stored encrypted local data meaningfully easier to brute-force — directly against the master prompt's security-first ordering. The legitimate version of this ask — a local app-lock PIN/biometric gate layered **on top of** the real password, never replacing or re-deriving the account credential — was flagged here for a dedicated pass rather than bolted on mid-flight; **now shipped, see "Biometric unlock ✅" below.**

### Image messages ✅ — a second slice of Phase 4 shipped early
Asked for directly, right after voice calling above landed. **Shipped**: a picked photo is downscaled (max 1600px on the long edge) and re-encoded to JPEG entirely client-side (`compressImageForSend` in `components/chat/message-thread.tsx`, canvas-based, retrying at lower quality if still too large) before it's encrypted through the same X3DH/Double-Ratchet envelope as text and voice (`contentTypeHint: 'image'`) — same inline-ciphertext path, same 4 MiB `MessageEnvelopeUpload.ciphertext` server-side cap (packages/types/src/messages.ts), no new server code at all. Tap-to-expand full-screen viewer, reply-preview and sidebar-preview both show "📷 Photo". Explicitly **not** the general media pipeline below: no originals preserved, no non-image files, no thumbnailing service — the compression happens because this is the same "fit it through a field sized for a voice note" trick, not a real upload system.

**A real, pre-existing bug found and fixed while building this, affecting voice messages too, not just new image ones:** `components/chat/chats-shell.tsx`'s sidebar-preview decrypt path (used when a message arrives for a conversation that isn't the currently-open thread) had its own separate `isVoice` check that only recognized `'voice'`, not the new `'image'` hint — so an image received while only the sidebar was open would've been reconstructed with `bytesToUtf8()` on raw JPEG bytes (garbage) and `mediaBase64: undefined`, permanently unrecoverable once the Double Ratchet key that decrypted it was gone. The same bug already existed for voice messages before this pass — a voice note received sidebar-only, then opened later, would have rendered as garbled text instead of a playable clip. Fixed by extracting the classification into one shared `lib/message-content.ts#hasMediaBytes`, imported by both `chats-shell.tsx` and `message-thread.tsx` instead of each keeping its own copy — the exact class of bug two independent "does this content type carry binary bytes" checks invites, now impossible by construction (docs/01-folder-structure.md's spirit, applied at function-level here rather than module-level). Verified via a live two-browser test that specifically exercises the sidebar-only path (B never opens the thread until after receiving the image) before this fix, then confirmed passing after it.

### Voice calling pass ✅ — a slice of Phase 6 shipped early
Real 1:1 audio calling, asked for directly right after the UI/polish pass above landed. **Shipped**: `call.*` signaling over the same authenticated WS channel as everything else (`server/realtime/message-handlers.ts`, [04-websocket-realtime](04-websocket-realtime.md#call-signaling)) — invite/ring, answer, ICE exchange, reject (declined/busy), end/hangup, all relayed blindly and authorized by re-deriving conversation membership, never a client-claimed device id; a client-side `RTCPeerConnection` (`components/call/call-provider.tsx`, mounted once at the app-shell level so an incoming call rings from any page, same reasoning as `RealtimeConnector`) with a 45s no-answer timeout, busy-guard against a second incoming ring while already on a call, and buffered ICE candidates for the (common) case where they arrive before the corresponding SDP has been applied; `POST /api/calls/turn-credentials` mints short-lived coturn `use-auth-secret` credentials, returning an empty ICE server list (not an error) until `TURN_SHARED_SECRET`/`TURN_URLS` are actually configured. Verified end-to-end with two real (headless, fake-device) browser sessions: ring → accept → both sides reach `connected` with a live remote `MediaStreamTrack` actually flowing → hangup propagates live to the other side; separately verified decline and immediate-redial (no stuck "busy" state).

**What this deliberately doesn't cover, tracked rather than glossed over:**
- **Video.** Explicitly out of scope for this pass (asked for as audio-only) — the signaling protocol is codec/media-type agnostic, so adding a video track later is a client-side + UI change, not a signaling redesign.
- **Group calls.** Phase 5 (groups) doesn't exist yet either; the whole design here is 1:1.
- **Call history.** ✅ Shipped in apps/mobile's push notification pass — `calls` rows are now written and updated as a call resolves (docs/02-database-schema.md), and `GET /api/calls/history` backs apps/mobile's "Calls" tab. No UI for this on apps/web itself yet (only the API + persistence landed; the tracked gap now is specifically "no web client screen for it," not "no history exists at all").
- **Minimize-to-bubble.** The call UI is a full-screen overlay for every phase including connected — there's no way to browse other chats while on a call yet (`components/call/call-overlay.tsx`'s docstring).
- **Actual coturn deployment.** This is real infrastructure ([11-deployment-architecture](11-deployment-architecture.md)) that has to be stood up on a real host with a public IP — not something achievable from an application-code pass. What shipped is everything on the app side that deployment needs (the credential-minting route, the env vars it reads); calls between peers on the same network work today via host candidates alone.

**Re-verified end-to-end, asked for directly** ("thoroughly check the calling and the voice message functionality... working perfectly without any issue"), alongside the group-chat/media-attachment pass below. Both re-confirmed live: ring→accept→both sides `connected` with a real, live remote `MediaStreamTrack`, decline, **immediate redial after decline** (not stuck in a false "busy" state), mute (`aria-pressed` genuinely toggles the outgoing track), and hangup propagating live to the other side — and separately, a voice message sent, received live via the sidebar-only path (thread not open), and played back with the correct decoded duration (byte-for-byte correct decrypt).

**One real, latent concurrency bug found and fixed while investigating a test failure during this pass** (the failure itself turned out to have a mundane cause — a malformed test-harness browser flag — but reading the decrypt path closely to rule that out surfaced a genuine, separate structural race): `chats-shell.tsx`'s sidebar-preview decrypt path and `message-thread.tsx`'s own catch-up/live decrypt path could both end up attempting to decrypt the *same* incoming message if a user taps into a conversation's thread in the narrow window between "the sidebar started decrypting a just-arrived message" and "the sidebar finished caching it." For the first message of a brand-new session this would be actively destructive (both attempts race on local one-time-prekey consumption and session state, and the loser can derive a different X3DH shared secret and decrypt into garbage), not just wasteful. Fixed with `decryptFromDeviceOnce` (`apps/web/lib/crypto/conversation-crypto.ts`) — memoizes an in-flight/just-resolved decrypt by the message's own (globally unique) id, so no matter how many call sites race to decrypt the same envelope, the real decrypt only ever runs once. Every decrypt call site in both components now goes through it.

### Push notifications ✅ — a slice of Phase 7 shipped early
Asked for directly, right after images above landed ("once a message... come[s], can we add notification"). **Shipped**: Web Push end-to-end — `components/notification-prompt.tsx` (an opt-in banner, top-right so it can never visually collide with `InstallPrompt`'s bottom-right one) subscribes via the real browser `PushManager`, `POST /api/push/subscribe` stores the subscription encrypted at rest (`packages/security`'s new `encryptAtRest`/`decryptAtRest`, AES-256-GCM, a server-held key — not the user's KEK, which nothing server-side can obtain) keyed by device; `apps/worker` subscribes to the same `MESSAGE_EVENTS_CHANNEL` Redis pub/sub `apps/web` already publishes `new`-message events onto ([04-websocket-realtime](04-websocket-realtime.md)) and, for any device with a stored subscription, sends a **generic** push payload — sender display name and conversation id only, e.g. "Alice sent a photo," never message content, since the server has no plaintext to include even if it wanted to (docs/09-trust-boundaries.md). `public/sw.js` shows the OS notification only if no window client is currently focused (the live WS delivery already covers the foreground case) and deep-links a click into the right conversation. `notification_preferences.conversations_default = 'none'` is honored (skips dispatch); a stale/revoked subscription's real 404/410 from the push service triggers automatic cleanup.

**A real, latent bug found and fixed while wiring this up, unrelated to push itself:** `server/realtime/ws-server.ts` created its Redis pub/sub subscriber at **module top-level** — which, because `server.ts` statically imports that module before ever calling `next({dev})`/`app.prepare()`, ran before Next.js had loaded `.env` into `process.env` at all. This only ever appeared to work because of a hardcoded `'redis://localhost:6379'` fallback that happened to match the real local dev value, silently masking a genuine ordering bug (removing that fallback to make `createRedisSubscriber()` strict, needed for the new shared helper below, immediately surfaced it: `REDIS_URL is not set`). Fixed by turning the module-top-level side effect into an exported `initRealtimeSubscriber()` function, called explicitly from `server.ts` inside `app.prepare().then(...)` — after Next's own env loading has actually run. Also extracted `createRedisSubscriber()` into `packages/security` (previously each pub/sub connection was hand-rolled with `new Redis(...)` at its call site) so `apps/worker`'s new push-dispatch subscriber and `apps/web`'s realtime subscriber share one implementation instead of two independent ones that could drift.

**What this deliberately doesn't cover:**
- **Notification preferences UI.** `conversations_default`/`show_preview` can only be changed by editing the database row directly today — no settings page ([03-api-design](03-api-design.md)'s `/push` section).
- **Rich/decrypted notification content.** `notification_preferences.show_preview` exists in the schema but currently has no effect — there is no path (yet) for a message to be decrypted and turned into a richer local notification, since a service worker has no access to the in-memory-only KEK a page holds. A real version of this would need the *page* (not the SW) to build the notification from an already-decrypted live WS message, only in the narrow case where push wouldn't have been needed anyway (page open, socket connected) — not implemented, since it doesn't cover the actual push use case (app not running).
- **Native/FCM path.** `provider: fcm` is reserved in the schema for a future native Android client; only `web_push` is implemented.

### General file attachments ✅ — the rest of Phase 4 shipped early
Asked for directly, identified as one of the two highest-value remaining gaps (alongside group chats) once asked "what's left." **Shipped**: a real signed upload/download object-storage pipeline (`packages/storage` — a `getObjectStorage()` factory choosing between a production S3-compatible adapter and a zero-setup local-filesystem dev adapter based on whether `OBJECT_STORAGE_*` env vars are configured, [11-deployment-architecture](11-deployment-architecture.md)), replacing the "squeeze it through the inline-ciphertext field" trick voice/images use for arbitrary files. A picked file is AES-256-GCM-encrypted client-side with a fresh random key/nonce (`lib/crypto/attachment-crypto.ts`, [05-crypto-architecture](05-crypto-architecture.md#media-encryption)), the ciphertext is uploaded to object storage, and only a small descriptor (`objectKey`/key/nonce/filename/mime-type/size) travels through the *existing* X3DH/Double-Ratchet message envelope as `contentTypeHint: 'media'` — no new crypto protocol, no new wire path for the E2E layer, only a new binary-transport side-channel the descriptor points at. `packages/storage` is shared by `apps/web` (the upload/download routes) and `apps/worker` (the new orphaned-object cleanup sweep in `jobs/cleanup.ts`, deleting uploaded-but-never-sent objects after 24h) — same "one shared implementation, not two that could drift" reasoning `createRedisSubscriber` already established for `packages/security`.

**Also shipped in the same pass, asked for separately right after**: WhatsApp-style **archive chat** (`ConversationMember.archived`, already sketched in the Phase 3 schema but never wired to anything) — a per-caller view preference, not shared with the other participant, `PATCH /api/conversations/:id`, a collapsible "Archived (N)" row in the sidebar. And the **Devices nav tab was removed** (still reachable at `/devices` directly, just no longer a header link) at the user's request — a UI simplification, not a feature removal.

**What this deliberately doesn't cover:**
- **EXIF/metadata stripping for general files.** Designed in [05-crypto-architecture](05-crypto-architecture.md#media-encryption) as a client-side default; not implemented for this pipeline (there's no generic way to "strip metadata" from an arbitrary file type the way there is for a re-encoded JPEG). The separate image-message pipeline strips EXIF as an incidental side effect of its own JPEG re-encode.
- ~~No per-account storage quota~~ — **closed by the media retention pass below**: a per-account running-total quota (`MEDIA_ACCOUNT_QUOTA_BYTES`) now sits alongside the per-file size cap (`MEDIA_MAX_UPLOAD_BYTES`, default 25 MB, enforced server-side regardless of client claims — a presigned-POST `content-length-range` condition in production, a streamed byte-count abort in the local dev adapter).
- **No resumable/chunked upload** — a dropped connection mid-upload means starting over.
- **No thumbnail/waveform generation.** `apps/worker` doesn't process attachment content at all yet (and structurally can't without keys it doesn't have — see [05](05-crypto-architecture.md#media-encryption)).
- **Real S3 was written but only verified via the local-fs adapter's exercised code path** (no cloud storage account was available to test against in this environment) — both adapters implement the identical `ObjectStorage` interface, and the S3 adapter's presigned-POST/GET calls are standard, well-trodden AWS SDK v3 usage, but this is flagged honestly rather than claimed as live-verified against a real bucket.

## Phase 4 — Media
General file attachments — signed upload/download, client-side AES-256-GCM attachment encryption — shipped early, see above (voice message recording/playback shipped even earlier, in the Phase 3 follow-up pass). ### Group chats ✅ — Phase 5 shipped early
Asked for directly, identified alongside general file attachments as the two highest-value remaining gaps. **Shipped**: real group conversations with a genuine Megolm-style group ratchet — `packages/crypto/src/group/ratchet.ts`, hand-implemented on the same `@noble/*` primitives and in the same reviewable style as the 1:1 Double Ratchet (mirrors its `kdfChainKey`/skipped-key-cache/header-encode structure directly), not a shared static key. Each member runs their own one-way outbound chain; every other member holds an inbound copy, delivered 1:1 over each member's *already-established* Double Ratchet session (`encryptForDevice`/`decryptFromDeviceOnce`, zero changes to that code) — confirmed reusable as-is during design.

Key distribution needed a transport docs/05's original design didn't specify — solved with a new durable outbox (`GroupKeyShare`, `server/modules/groups/key-share-service.ts`): a live WS `group.key-share` ping plus a `GET /groups/:id/key-shares` REST catch-up, so a briefly-offline member never permanently misses a session. `sendMessage` (`server/modules/messages/service.ts`) generalized from one recipient device to a fan-out loop over every other current member's primary device — the same `MessageRecipient`/`MessageDto` shapes, no schema break. Removing a member bumps the group's epoch, deletes their `ConversationMember` row (immediate access loss via the existing `requireConversationMembership` gate — no new check needed), and every remaining member's client reacts to a `group.members-changed` event by rotating to a fresh outbound session and redistributing only to the current member set; adding a member shares the *current* session, going forward only. Verified live end-to-end (three real browser sessions): create → send/receive text, voice, and sender-name-labeled bubbles → remove a member → the removed member is denied server access entirely *and* the remaining members' next message is unreadable to them → re-add the same member → they receive new messages but do **not** retroactively see what was sent while they were out, while still holding their own earlier pre-removal history.

**Two real bugs found and fixed while building this, both via live testing that a unit-test suite wouldn't have caught:**
- **A fire-and-forget WS send silently dropping.** Key-shares were originally sent via `sendRealtimeEvent`, which drops silently if the socket isn't open yet (`lib/realtime-client.ts`'s own documented behavior) — reliably reproducible by sending a group's very first message immediately after creating it, before the just-mounted thread's socket finished connecting. Fixed by making `POST /api/groups/:id/key-shares` the primary send path (durable regardless of socket timing); the WS inbound case still exists as a redundant fast path when a socket happens to already be open.
- **React StrictMode's dev-mode double-effect-invocation double-decrypting a message.** `GroupMessageThread`'s mount-time catch-up effect running twice (by design, in dev) meant the same group message got decrypted twice — correctly on the first attempt, then correctly *refused* on the second (the one-way ratchet had already advanced past that counter, which is right — the bug was calling it twice, not the ratchet's response to that). The 1:1 path never hit this because its own decrypt path was already memoized by message id (see the calling/voice-message regression section above); fixed by adding the identical memoization (`decryptGroupMessageOnce`) for groups.

**What this deliberately doesn't cover, flagged rather than glossed over:**
- **No invite links.** Members are added directly by any current member (admin-only for removal); join-by-link is out of scope.
- **No promote/demote UI.** The `role` field and its enforcement (`onlyAdminsCanMessage`) exist; no route changes a member's role after creation.
- **No group avatar upload**, no "read by N" receipt aggregation UI (per-recipient delivery/read rows are still recorded, just not surfaced), no group voice/video calls (calling stays explicitly 1:1), no typing indicators in groups.
- Same tracked gap 1:1 already has: fan-out targets one device per *other* member, not the sender's own additional devices.

### Media retention ✅ — a Phase 9/10 storage-bounding measure shipped early
Asked for directly: with media now flowing freely (voice notes, photos, general files), unbounded storage growth needed an answer that didn't wait for a dedicated "performance/hardening" phase. **Shipped**: images, voice notes, and file attachments have their content erased 24 hours after being sent, always — a new `apps/worker` sweep (`sweepExpiredMedia`, `jobs/cleanup.ts`) independent of the existing disappearing-message sweep, since this is a storage default every conversation is on, not a privacy setting anyone opts into (see [10-privacy-data-retention](10-privacy-data-retention.md)'s "Media retention" section for the full reasoning on why it's deliberately *not* folded into `DisappearingTimer`). Text messages are untouched.

Mechanically, this reuses the exact tombstone shape the disappearing-timer sweep and manual delete already established (`deleted_at` set, `ciphertext`/`envelope_header`/`x3dh_init` nulled) — the only schema addition is `messages.deletion_reason` (`manual` | `disappearing_timer` | `media_retention`), so all three paths can share one tombstone mechanism while the client still shows the right placeholder for each ("This message was deleted" vs. "This photo has expired"). For a `media`-type (file) message, the sweep also deletes the underlying object-storage blob before tombstoning the row — genuinely reclaiming the space, not just hiding a live pointer to it. The `deleted` realtime event gained a `reason` field so an already-open thread updates its placeholder text live, not just on next reload.

Added an explicit Download button to `ImageBubble`/`VoiceBubble` in the same pass (`FileBubble` already had one) — always visible on the bubble itself, not tucked behind a menu, specifically because these two content types are now the ones with a hard 24h clock on them.

**Flood protection, shipped in the same pass** — a 24h expiry alone doesn't stop an account from uploading enough, fast enough, to exhaust a self-hosted server's disk *within* that window:
- **Per-account storage quota** (`MEDIA_ACCOUNT_QUOTA_BYTES`, default 500 MiB) — `POST /media/upload-url` now sums the caller's currently-live (non-expired, non-deleted) attachment bytes and rejects with `QUOTA_EXCEEDED` if a new upload would exceed it. Closes the gap the file-attachments pass above explicitly flagged as open.
- **A second, tighter rate-limit bucket for inline media** (`mediaMessageSend`, 20/min) layered on top of the existing 120/min `messageSend` limit, specifically for `image`/`voice` content — these never touch the upload route (they ride inline in the message ciphertext), so the quota above doesn't see them; this bounds that path the same way.
- **Orphaned (uploaded-but-never-sent) objects are reclaimed after 1 hour, not 24** — `apps/worker`'s `sweepOrphanedMediaObjects` cutoff was tightened; the Redis record linking an upload to a pending send already expires after 10 minutes, so a full day's grace period for the actual bytes was unnecessarily generous and the more exploitable half of a "flood via upload, never send" attempt.

**What this deliberately doesn't cover:**
- **No per-conversation override.** Can't turn this off for a specific chat the way disappearing messages can be turned on — a real, tracked follow-up, not built this pass (see reasoning above).
- **No "expiring soon" warning.** The download button is the mitigation; there's no countdown UI telling a user a specific photo has N hours left.
- **A device that never saw a message before it expires never sees anything at all**, not even a placeholder — same pre-existing limit disappearing messages and manual deletes already have (`listMessages` filters `deleted_at: null` out of history entirely), not a new gap this feature introduces.

### Security headers / CSP ✅ — a slice of Phase 9 shipped early

Asked for directly, after being asked "what's left before going live" and answering with a prioritized list — this was the pick made ("my own pick would be security headers + CSP") since it closed real exposure with no product decisions needed. **Shipped**: `apps/web/middleware.ts` (new — no middleware existed before this), plus `Strict-Transport-Security` in `next.config.mjs` (production only) — see [11-deployment-architecture](11-deployment-architecture.md)'s Security headers section for the full directive-by-directive rationale.

**A real bug found and fixed via live testing, not typecheck/lint/build (all three stayed clean throughout):** the first version built the CSP as a static `next.config.mjs` config, allowing the one inline script this app's own code renders (`app/layout.tsx`'s dark-mode-before-paint snippet) via a `sha256-` hash computed from its actual source. This looked correct and matched the letter of [11-deployment-architecture](11-deployment-architecture.md)'s "no `unsafe-inline` unless documented" rule — but loading the login page in a real browser immediately showed the app fully unhydrated (a Next.js invariant error, forms falling back to native submission). The App Router injects several *of its own* inline `<script>` tags per page (streamed RSC payload chunks), whose content is the actual page data and therefore different on every request — no static hash could ever have covered them, and a static per-app CSP config was the wrong shape for this framework from the start, not just missing a case. Fixed by switching to Next's own documented pattern instead: `middleware.ts` mints a random nonce every request, forwards it to `app/layout.tsx` (the one inline script not auto-covered by Next's own nonce-stamping) via `next/headers`, and `'strict-dynamic'` in `script-src` extends trust from that nonce to whatever those hydration scripts load in turn.

**What this deliberately doesn't cover:**
- **`style-src 'unsafe-inline'`** — a documented, narrow exception, not an oversight; see [11-deployment-architecture](11-deployment-architecture.md)'s note on why `script-src` (not `style-src`) is where a strict policy actually matters.
- **Not live-verified against a real coturn or S3 deployment** — the `connect-src` logic for both is written and reasoned through, but (same honest flag as the file-attachments pass's S3 adapter) neither has actually been exercised against real infrastructure in this environment.
- **A handful of previously-statically-optimized routes (`/login`, `/`) now render dynamically.** `app/layout.tsx` reading the nonce via `headers()` opts its entire subtree out of static generation — every route shares that root layout. A known, inherent trade-off of Next's own nonce-based CSP pattern (not something this pass introduced avoidably), and a small one on an app that's already server-rendering everything else and running behind rate limits — not a regression worth engineering around.
- **The rest of Phase 9** — MFA/TOTP step-up, `blocked_users` enforcement, dependency/secret scanning in CI, Security Center + Privacy Center UI, and an external review of `packages/crypto` (Phase 11) — is still open; this pass was scoped to headers/CSP specifically, not all of Phase 9.

### Biometric unlock ✅ — the deferred half of the Phase 3 follow-up pass, shipped

Asked for directly ("once he adds the PWA... can he turn on the fingerprint... to login"), following up on the "Biometric/PIN unlock" idea explicitly deferred earlier in this roadmap. **Shipped exactly the legitimate version described there** — layered on top of the real password, never replacing or re-deriving it: `lib/crypto/biometric-unlock.ts` registers a platform-authenticator WebAuthn credential (Touch ID/Face ID/Windows Hello/Android biometrics — `authenticatorAttachment: 'platform'`, `userVerification: 'required'`, never a roaming security key) with the PRF extension requested. Evaluating that credential against a fixed, non-secret salt deterministically reproduces the same secret bytes, only on this device, only after the actual biometric/PIN gate — that secret (normalized to a proper key via `hkdfSha256`, newly exported from `@comm/crypto` for this) wraps the already-Argon2id-derived KEK exactly the way every other piece of local key material is already wrapped (`wrapBytes`/`unwrapBytes`) — not a new storage mechanism, just a new way to unlock the existing one. The account password itself is never touched, stored, or weakened.

Two halves: `components/biometric-unlock-toggle.tsx` (enrollment — lives on the Devices page specifically because this is a per-device local credential, the same "identity lives per-device" model everything else in `lib/crypto/` already follows, not a server-side account setting) and `unlock-gate.tsx` (use — offers a biometric button alongside, never instead of, the password field, for the exact "session's still valid, KEK's just not in memory" case that gate already existed to handle). PRF support is genuinely inconsistent across browsers (flagged in the original deferral) — every function in `biometric-unlock.ts` fails closed to `false`/`null`, never throws, so an unsupported device/browser combination or a cancelled OS prompt just leaves the password field as the only option, exactly as if the feature didn't exist there.

**Found and fixed in the same pass, not shipped separately:** a biometric enrollment wraps the KEK as it existed *at enrollment time* — a password change elsewhere re-derives a new KEK the old wrapped one doesn't match, the same "local data doesn't get re-wrapped after a password change" gap `login-form.tsx`'s own docstring already flags for the account's core identity blob. `unlockWithBiometrics` fails closed (`null`, not a thrown error) in exactly this case, the same defensive posture `sessions.ts#loadSession` already applies to a stale session — and `change-password-form.tsx` now proactively clears a biometric enrollment on a successful password change, rather than leaving a button that's silently guaranteed to fail from that point on.

**What this deliberately doesn't cover:**
- **No re-wrap-on-password-change for the *account identity* itself** — the pre-existing gap this pass's fix is modeled on is still open; this pass only makes sure biometric unlock fails gracefully against it, not that the underlying gap is closed.
- **Not live-verified against a real platform authenticator** — this development environment has no Touch ID/Windows Hello hardware to test against; the WebAuthn/PRF call shapes match the spec and MDN's documented usage exactly, but this is flagged honestly rather than claimed as live-tested, the same posture already taken for the S3 storage adapter and the CSP `connect-src` logic against a real coturn deployment.
